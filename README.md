# KubeOps Agent (GitBot)

A GitOps webhook bot that bridges pull request activity with [ArgoCD](https://argo-cd.readthedocs.io/) application deployments. When a developer opens a PR or runs a bot command, GitBot automatically points the target ArgoCD application to the PR branch — enabling full-environment testing before merge. It also blocks merges while a deploy is active, preventing branch drift.

```
PR opened / #argo deploy
        │
        ▼
   GitBot webhook
        │
        ├─ Validates PR state (approvals, commits behind)
        ├─ Matches changed files → ArgoCD apps
        ├─ Sets spec.source.targetRevision = PR branch
        └─ Posts status comment on PR
```

---

## Features

- **Automatic deploy-on-open** — lock apps as soon as a PR is created
- **Bot commands in PR comments** — `#argo deploy`, `#argo unlock`, `#argo help`, and more
- **Automatic unlock on merge/decline** — restores the original branch with no manual action
- **Multi-cluster support** — central instance fans out to remote GitBot agent instances
- **Kubernetes admission webhook** — blocks external targetRevision changes while an app is locked
- **ArgoCD deployment notifications** — posts ArgoCD sync status back to the PR
- **Security rules** — restrict lock/unlock per repository, file pattern, and user/group
- **Bot self-ignore** — events generated by the bot's own account are silently discarded

---

## How It Works

1. Bitbucket sends a webhook to GitBot on PR events (open, update, merge, decline, comment).
2. GitBot enriches the event: fetches changed files and how many commits the branch is behind.
3. The event is validated (approvals, no pending change-requests, branch is up to date).
4. Matching ArgoCD apps are found by repository URL and file paths.
5. GitBot patches `spec.source.targetRevision` on the matched apps via the Kubernetes API.
6. A comment is posted on the PR with the operation status.
7. On merge or decline, all apps locked by the PR are automatically restored.

## Requirements

- Kubernetes cluster with ArgoCD installed in the `argocd` namespace
- Bitbucket Cloud account and a repository webhook configured to point at GitBot
- Go 1.22+ (for building from source)

## Quick Start

### 1. Clone

```bash
git clone https://github.com/your-org/kubeops-agent.git
cd kubeops-agent
```

### 2. Configure environment

Copy the example and fill in your values:

```ini
# env.ini
HTTP_PORT=8080
BITBUCKET_BEARER_TOKEN=<bitbucket-api-token>
WEBHOOK_TOKEN=<shared-secret-for-webhook-validation>   # optional
API_TOKEN=<bearer-token-for-gitbot-api>                # optional
CONFIG_FILE=config.yaml
CLUSTER_NAME=my-cluster
BOT_KUBERNETES_USERNAME=system:serviceaccount:argocd:gitbot
BITBUCKET_BOT_UUID=<uuid-of-the-bot-bitbucket-account> # optional, prevents self-loops
```

### 3. Configure clusters and security rules (optional)

```yaml
# config.yaml
clusters:
  - name: production
    auth:
      type: serviceaccount   # uses the in-cluster service account

  - name: staging
    auth:
      type: agent
      url: https://staging.example.com/gitbot
      insecure-skip-tls-verify: false   # set true only in non-production

security:
  groups:
    - name: platform-team
      users:
        - alice@example.com
        - bob@example.com

  rules:
    - repository: https://bitbucket.org/your-org/your-repo.git
      filepattern: ["overlays/production/**"]
      action: ["lock", "unlock"]
      group: ["platform-team"]
      user:
        - charlie@example.com
```

> When no security rules are defined every user can lock and unlock any app.

### 4. Run locally

```bash
go run ./cmd/server/main.go
```

## Deployment on Kubernetes

Apply the bundled manifests (edit the image tag and Secret first):

```bash
# Create the Secret from your env.ini values
kubectl create secret generic gitbot \
  --namespace argocd \
  --from-literal=HTTP_PORT=8080 \
  --from-literal=BITBUCKET_BEARER_TOKEN=<token> \
  --from-literal=API_TOKEN=<api-token> \
  --from-literal=CLUSTER_NAME=production

# Deploy
kubectl apply -k manifests/
```

The RBAC manifest grants GitBot `get/list/watch/patch/update` on `argoproj.io/applications` cluster-wide — no other permissions are needed.

### Container image

```bash
# Build with Podman
podman build --platform linux/amd64 -f Containerfile -t your-registry/gitbot:latest .

# Push
podman push your-registry/gitbot:latest
```

## ArgoCD Application Annotations

GitBot reads and writes these annotations on ArgoCD Application resources:

| Annotation | Purpose |
|---|---|
| `bot.gitbot.io/locked` | `"true"` while the app is locked by a PR |
| `bot.gitbot.io/pull-request` | ID of the PR holding the lock |
| `bot.gitbot.io/rollback` | Branch to restore when unlocked |
| `gitbot.io/env` | Environment label read for filtering (`"dev"`, `"prod"`, …) |
| `gitbot.io/contain-other-apps` | `"true"` for app-of-apps patterns |
| `argocd.argoproj.io/manifest-generate-paths` | Base path used for file-to-app matching |

Example ArgoCD Application:

```yaml
metadata:
  annotations:
    gitbot.io/env: "dev"
    argocd.argoproj.io/manifest-generate-paths: /overlays/dev
```

## Bot Commands

Commands are parsed from PR comments in the format:

```
(/|#)(argo|flux|bot) <command> [environment] [app-name]
```

| Comment | Effect |
|---|---|
| `#argo deploy` | Lock all matching apps across all environments |
| `#argo deploy dev` | Lock apps in the `dev` environment only |
| `#argo deploy dev my-app` | Lock a specific app in the `dev` environment |
| `#argo lock` / `#argo test` | Same as `deploy` |
| `#argo unlock` | Unlock all apps locked by this PR |
| `#argo unlock dev` | Unlock apps in `dev` only |
| `#argo rollback` / `#argo undeploy` | Same as `unlock` |
| `#argo help` | List available environments and commands |

Lock is also triggered automatically when a PR is opened (if matching apps exist), and unlock happens automatically on PR merge or decline.

## Pre-deploy Validations

Before locking, GitBot checks:

| Check | Failure message |
|---|---|
| At least one reviewer has approved | "You need at least one approval from a reviewer" |
| No reviewer has requested changes | "One of the reviewers has requested changes" |
| Branch is up to date with destination | "This pull request is N commits behind 'main', sync your branch!" |

## Multi-Cluster Setup

GitBot supports a hub-and-spoke model: a central instance (hub) manages multiple remote clusters by delegating to lightweight agent instances (spokes).

```
                  ┌─────────────────────┐
 Bitbucket ──────▶│   Central GitBot    │
                  │   (hub cluster)     │
                  └───────┬─────────────┘
                          │ HTTP (API token)
              ┌───────────┴────────────┐
              ▼                        ▼
   ┌──────────────────┐    ┌──────────────────┐
   │  GitBot Agent    │    │  GitBot Agent    │
   │  (staging)       │    │  (production)    │
   └──────────────────┘    └──────────────────┘
```

Configure remote clusters with `type: agent` in `config.yaml`:

```yaml
clusters:
  - name: hub
    auth:
      type: serviceaccount

  - name: staging
    auth:
      type: agent
      url: https://gitbot.staging.example.com
```

The central instance proxies lock/unlock operations to the correct agent based on the `Cluster` field of each ArgoCD app. All results are aggregated into a single PR comment.

## Kubernetes Admission Webhook (optional)

GitBot ships an admission webhook endpoint that prevents any actor other than the bot's own service account from changing `spec.source.targetRevision` on a locked app.

**Endpoint:** `POST /api/v1/admission/apps/validate`

Register it as a `ValidatingWebhookConfiguration` pointing at this endpoint. Set `BOT_KUBERNETES_USERNAME` to the service account's username (e.g. `system:serviceaccount:argocd:gitbot`).

---

## Deployment Notifications

ArgoCD can call back into GitBot to post sync status on the locked PR:

**Endpoint:** `POST /api/v1/notification` (requires API token)

```json
{
  "app_name": "my-app",
  "message": "✅ Synced successfully"
}
```

GitBot looks up the app, checks if it is locked, and posts the message on the corresponding PR.

## REST API

All endpoints except `/api/v1/status` and the webhook require the `Authorization: Bearer <API_TOKEN>` header when `API_TOKEN` is set.

| Method | Path | Description |
|---|---|---|
| `GET` | `/api/v1/status` | Health check |
| `POST` | `/api/v1/webhook/bitbucket` | Bitbucket webhook receiver |
| `GET` | `/api/v1/apps` | List all ArgoCD apps |
| `POST` | `/api/v1/apps/{id}/lock` | Lock an app to a branch |
| `POST` | `/api/v1/apps/{id}/unlock` | Unlock an app |
| `POST` | `/api/v1/notification` | Post a deployment notification to a PR |
| `POST` | `/api/v1/admission/apps/validate` | Kubernetes ValidatingAdmissionWebhook |

## Adding a Git Provider

Implement the `types.Provider` interface and register a new webhook route:

```go
// internal/event/provider/github.go
type GitHubProvider struct { ... }

func (g *GitHubProvider) ParseEvent(headers http.Header, body io.ReadCloser) (types.Event, error) { ... }
func (g *GitHubProvider) GetData(e types.Event) (types.Event, error)                             { ... }
func (g *GitHubProvider) WriteComment(repo string, prId, parentId int, msg string) error         { ... }
func (g *GitHubProvider) WriteEventResponse(...) error                                            { ... }
func (g *GitHubProvider) ValidateWebhookToken(secret string, h http.Header, body []byte) error   { ... }
```

Then add a route in `cmd/server/main.go`:

```go
github := provider.NewGitHubProvider(...)
router.HandleFunc("POST /api/v1/webhook/github", internal.EventCreate(eventQueue, github, c.WebhookToken))
```

## Architecture

GitBot follows the **Pure Core / Imperative Shell** pattern:

- **Pure core** (`internal/types/`, `internal/event_process_v1.go`) — domain logic in pure functions with no side effects. Easy to unit-test without mocks.
- **Imperative shell** (use cases in `internal/*.go`) — orchestrates I/O calls to adapters and passes results to pure functions.
- **Adapters** (`internal/adapters/`) — translate between external systems and domain types. No business logic lives here.
